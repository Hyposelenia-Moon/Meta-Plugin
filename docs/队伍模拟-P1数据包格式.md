# 队伍模拟 P1 数据包格式

> 面向录入者：这份文档说明「一份数据包长什么样、每个字段的单位与来源要求、校验会拒什么」。
> 内核只认这里写的字段，不认额外字段，也不补默认值。

- 相关代码：`src/modules/teamSimulation/dataPack.ts`、`rotation.ts`、`timeline.ts`、`teamRun.ts`
- 示例包：`test/fixtures/team-sim/example-pack.json`（**全部为合成占位值，不是游戏数据**）
- 加载与验收：`test/team-sim-pack.test.mjs` 会原样读取示例包，`validateDataPack` 必须无问题，并跑通一轮 `simulateTimeline`

## 1. 这份文档不提供什么

- 不含任何真实帧表、倍率、产球或机制数值；示例包里的数都是占位值。
- 不解释机制细节。真实数值必须来自版本化数据包，并写清 `gameVersion` 与 `source`。

## 2. 数据包 `DataPack`

```ts
interface DataPack {
  schemaVersion: 1
  gameVersion: string   // 数据对应的游戏版本，如 "7.1"
  source: string        // 出处，如 "miao-plugin@<sha> 抄录" 或 "手抄自 XX"
  actions: Record<string, ActionSpec>  // 键必须等于动作自身的 id
  effects?: Record<string, EffectSpec> // 键必须等于效果自身的 id；命中触发按这张表结算
}
```

校验（`validateDataPack`）：`schemaVersion` 不等于 1 → `version-mismatch`；`gameVersion`、`source` 去空白后为空 → `invalid`/`missing`；`actions` 为空 → `invalid`；动作 `id` 与键不一致 → `invalid`；每条动作再走 `validateActionSpec`；`effects` 里每条走 `validateEffectSpec`；动作命中里的 `triggerIds` 找不到对应效果 → `unsupported`。

## 3. 动作 `ActionSpec`

```ts
interface ActionSpec {
  id: string
  actorId: string
  kind: 'normal' | 'charged' | 'plunge' | 'skill' | 'burst' | 'switch'
  timing: { type: 'frames'; frames: number }
        | { type: 'response'; k: number; bMs: number }
  hits: HitSpec[]
  cancelWindows?: { fromFrame: number; toFrame: number }[]
  particles?: ParticleSpec[]
  energyCost?: number
  cooldownFrames?: number
  cooldownId?: string
  requires?: string[]
  mechanism?: string
}
```

| 字段 | 单位 | 说明 |
|---|---|---|
| `timing.type = 'frames'` | 帧 | 计时器型：帧数与帧率档位无关；换档位只改毫秒 |
| `timing.type = 'response'` | `k` 无量纲、`bMs` 现实毫秒 | 响应型：现实时长 = `k × 帧生成时间 + bMs`，再按档位向上取整成帧 |
| `hits[].atFrame` | 帧 | 命中相对动作起手的偏移，必须是非负整数、递增，且小于动作帧数 |
| `cancelWindows` | 帧 | 可取消区间；终点不能超过动作帧数 |
| `particles[].travelFrames` | 帧 | 粒子飞行帧数，到达时才回能 |
| `energyCost` | 能量点 | 起手扣，不受本轮产球影响 |
| `cooldownFrames` | 帧 | 从起手帧开始计，冻结期内的部分顺延 |
| `mechanism` | 标记 | 声明这段动作触发 P1 机制层建模的角色机制（见下节表格）；为空或未知标记都会被拒 |

`timing` 必填、没有默认：`k` 或 `bMs` 为负、二者同时为 0、`type` 未知，都会被拒。

### 机制标记 `mechanism`

P1 只建模纯岩试点这四个角色的机制，值必须是下表的字符串之一，且动作的 `actorId` 必须是该机制的主人：

| 标记 | 主人 | 机制效果 |
|---|---|---|
| `itto-q` | 一斗 | 开启后按防御力提高攻击（`×1.0368`），持续 11 秒 |
| `itto-na2` / `itto-na4` | 一斗 | 命中给 1 / 2 层乱神之怪力（上限 5、60 秒） |
| `itto-charged` | 一斗 | 每段消耗 1 层；层数为 0 时记违规（不是崩溃，是能被测试断言的问题） |
| `gorou-e` | 五郎 | 按队伍岩元素角色数分档：≥3 名才给岩伤加成，另给固定防御 371.09，持续 12 秒 |
| `zhongli-hold-e` | 钟离 | 玉璋护盾使附近敌人全抗与物抗 -20%（全场、不叠加、20 秒） |
| `albedo-e` | 阿贝多 | 阳华领域每 2 秒生成一次刹那之花（按防御、240.48%），持续 30 秒 |

窗口类机制只在施放者**处于前台**的区间生效（一斗 Q、五郎 E）；队伍级与召唤物类的（钟离减抗、阿贝多阳华）不切片。召唤物命中不进事件队列，由结算层按帧展开——这是已知限制，不是 bug。

机制层只接受 `scheduler: 'fixed'`；`asap-sequence` 与 `wait` 步骤会直接报 `unsupported`，因为帧数未知时没法定窗口，猜一个数只会骗自己。

## 4. 命中 `HitSpec`

```ts
interface HitSpec {
  atFrame: number
  motionValue: number                 // 倍率；乘哪项面板由 scaling 决定
  scaling: 'atk' | 'hp' | 'def'       // 必填：阿贝多按防御结算这类差异靠它表达
  element: 'geo' | 'physical'         // P1 只支持岩与物理
  canCrit: boolean
  triggerIds?: string[]
  hitlagFrames?: number               // 这一段命中造成的卡肉帧数
}
```

- `scaling` 缺省 → `missing`；未知值 → `unsupported`。
- `triggerIds` 是效果表的入口：必须是数组，元素必须是非空白字符串，否则 `invalid`；每个 id 必须在 `effects` 表里登记，否则 `unsupported`。
- `hitlagFrames` 必须是非负整数，只写在命中层（动作层没有这个字段，两处并存会说不清是谁的卡肉）。
- 元素命中结算时读 `stats.dmg + stats[element]`，物理命中只读 `stats.phy`。

**卡肉**：`hitlagFrames: H` 表示这一发命中造成 `H` 帧冻结，窗口 `[命中帧, 命中帧 + H)` 内游戏时钟停走。实现上把冻结期内排在这之后的一切整体顺延 `H` 帧——后续命中、产球到达、动作收尾、冷却期限、效果到期——现实帧照常消耗。所以同一个动作会变长，而游戏内时间不变：

```text
realMs = 结束帧 × 帧生成时间
gameMs = (结束帧 − 累计卡肉帧数) × timerTickMs
```

请求帧落在冻结里时：`fixed` 直接拒绝（路径 `steps.<id>.hitlag`，消息里报最早可行动帧）；`asap-sequence` 顺延到冻结结束，结果里同时记请求帧与实际帧；切人同理顺延。请求帧正好等于命中帧时也先结算这一发再判断，动作不会在冻结期里起手。同一帧的多段命中共用一段冻结、不叠加顺延，累计卡肉帧数按合并后的区间算。卡肉时长来自数据、P1 不校准，只要用过卡肉，结果就是 `approximate`，并在 `approximateItems` 里留一条。

## 5. 效果 `EffectSpec`

```ts
interface EffectSpec {
  id: string
  target: 'self' | 'team' | 'enemy'   // 前两者加面板，enemy 减抗减防
  stats?: Partial<Record<PanelStatKey, number>>  // 与面板同单位相加
  enemy?: { resistanceReduction?: number; defenseReduction?: number; defenseIgnore?: number; resistanceByElement?: Partial<Record<ElementKey, number>> }
  durationFrames?: number             // 省略 = 持续到测量窗口结束
  stacking?: 'refresh' | 'stack' | 'ignore'  // 缺省 refresh
  maxStacks?: number                  // 只有 stack 可以写
}
```

| 字段 | 说明 |
|---|---|
| `stats` | 面板增量。`atk/hp/def/mastery` 是数值，`cpct/cdmg/recharge/dmg/phy/heal` 与元素键是比例；`hpPct` 这类构筑期百分比不在其中，写了直接 `unsupported` |
| `enemy` | 只对 `target: 'enemy'` 有效；`resistanceReduction: 0.2` 表示全抗性降 0.2；`resistanceByElement: { dendro: 0.3 }` 仅降草抗。元素键须合法，减益须为有限数值（公式里是 `抗性 − 减抗`） |
| `durationFrames` | 从触发帧起算；省略表示到窗口结束 |
| `stacking` | `refresh` 刷新到期、不叠层；`stack` 叠层至 `maxStacks`；`ignore` 已存在时不重复施加 |
| `maxStacks` | 仅 `stack` 可用；叠层策略缺上限、或非叠层策略写上限，都会被拒 |

触发语义：命中先按**当帧已生效**的修饰结算伤害，再结算它自己携带的触发。所以「给自己上攻击力」的那一下不吃自己的加成，后续命中与同队其他角色才吃。队伍效果（`team`）作用于 `rotation.actors` 登记的全部角色；敌人减益是全局量，任何角色命中都读同一份。每次实际生效的触发写进 `TimelineResult.triggers`，窗口结束时的存续状态写进 `effects`。

## 6. 帧率档位 `FrameTier`

```ts
interface FrameTier { id: string; fps: number; timerTickMs: number; source: string }
```

`FRAME_TIERS` 里预置 8 档（来自《原神帧率学》BV1Z8rLBGEeo 的计时器型档位表，第一列是解锁插件里输入的帧数）：

| id | fps | timerTickMs |
|---|---|---|
| `fps-56` | 56.31477 | 18 |
| `fps-60` | 60.36144 | 17 |
| `fps-64` | 64.41135 | 16 |
| `fps-73` | 73.5355 | 14 |
| `fps-104` | 105.0891 | 10 |
| `fps-217` | 221.7778 | 5 |
| `fps-384` | 399.1304 | 3 |
| `fps-625` | 665.7423 | 2 |

约束：`timerTickMs` 必须等于 `round(1000 / fps)`，否则一帧到底多长没有唯一答案，`validateFrameTier` 直接拒。档位必须由轴显式给出，内核不设默认。

## 7. 轴 `RotationSpec`

```ts
interface RotationSpec {
  id: string
  scheduler: 'fixed' | 'asap-sequence'
  frameTier: FrameTier
  measurementEndFrame: number
  steps: TimelineStep[]           // { kind:'action', actorId, actionId, atFrame? } | { kind:'switch', actorId, atFrame? } | { kind:'wait', frames }
  actors: ActorInit[]             // { actorId, energy, energyMax }
  activeActorId: string
  switchFrames?: number
  energyRecharge?: Record<string, number>
  stateFlags?: string[]
}
```

校验（`validateRotation`）：帧率档位、测量窗口、步骤类型、动作是否在包里、`atFrame` 是否非负整数、**步骤 id 是否重复**（重复会让报错路径与请求记录指向同一处）、**等待步骤是否误写了 `atFrame`**、角色是否重复登记、初始能量是否越界、初始前台是否在角色表、**步骤里出现的角色是否都在 `rotation.actors` 登记**、充能效率是否为正有限值、**充能效率的键是否都是已登记角色**（写错 id 会被内核查不到而静默忽略，所以直接拒）。

换人与出手动作同口径，三条约束都写在核心里：

- 请求帧不能早于「上一动作最早可取消帧」——压在动作里就换不出去，报 `steps.<id>.atFrame` 并给出可换人的帧。换人后的最早可行动帧是 `换人帧 + switchFrames`（`switchFrames` 省略当 0）。
- 换人会取消上一动作尚未发生的命中与产球：后摇被换人打断，落空的那几段不再结算，也不会留下 `action-end`。
- 换人请求同样受测量窗口约束（`atFrame` 超出窗口直接拒）；请求帧落在卡肉冻结期里则顺延到冻结结束，结果里同时记请求帧与实际帧。

## 8. 单位与取整

- 帧一律整数，不做四舍五入；小数帧直接拒绝。
- 计时器型：动作占 `frames` 帧；游戏时长 = `frames × timerTickMs`，现实时长 = `frames × 1000 / fps`。
- 响应型：现实时长 = `k × (1000/fps) + bMs`；折算帧数 = `ceil(现实时长 / (1000/fps))`，因为引擎逐帧检查动作是否结束。
- `计时器时间 = (1000/fps) / timerTickMs`：小于 1 是快帧，大于 1 是慢帧；技能文本里的「一秒」对应 `计时器时间` 个现实秒。
- 卡肉：现实时长包含冻结帧，游戏时长扣掉它们。`timing.hitlagFrames` 是整轮累计的冻结帧数，`timing.realMs` 用结束帧算，`timing.gameMs` 用 `结束帧 − hitlagFrames` 算。

## 9. 编排入口 `simulateTeam`

```ts
simulateTeam({ pack, rotation, members, expected, targetPresetId, crit, debuffs, mode? })
```

`mode` 两种取值，缺省 `dps-standard`：

- `dps-standard`：强制 110 级小宝、10% 抗性、120 秒窗口、0 初始能量（见第 12 节）。四项任一不符就地拒绝，并在 `dps-standard` 关点名路径。
- `diagnostic`：内部诊断口径，跳过标准检查、结果 `dps` 为 `null`。必须显式传入，不会因为「忘了写 mode」而悄悄降级。

按顺序过关，任一关不过就整轮拒绝并停下：数据包 → 版本一致性（包 `gameVersion` 必须等于 `expected.gameVersion`）→ 轴 → DPS 标准（仅 `dps-standard`）→ 成员面板（每人 `validateCharacterBuild` + `buildPermanentStats`）→ 机制层（窗口、召唤物、层数与资源合法性）→ 时间线 → 结算。结果里的 `checks` 列出每关状态与问题路径，`versions` 透出实际用到的包版本与面板版本，`mode` 与实际目标也一并返回；`simulationReady` 恒为 `false`。

版本不一致直接拒，不设「只警告」开关：帧表来自一份版本、属性表来自另一份，跑出来的数没有统一基准。

每关状态与整轮状态用同一套归类：有 `unsupported` 先报 `unsupported`，其次 `invalid`，只剩缺字段才是 `incomplete`——缺字段（例如没给 `expected.gameVersion`）与写错值是两种修法，不能都塞进 `invalid`。

测量窗口只管「动作起手能不能排进来」，不管动作跑多久：起手在窗口内、收尾在窗口外的动作照样跑完，`timing.realMs` 与 `gameMs` 覆盖到实际收尾帧。

结果整理：`buildTeamRunReport(result)` 把一轮结果摊平成摘要（关状态、版本、窗口、每角色/每动作合计、触发次数、近似项、失败问题），`formatTeamRunReport(report)` 再排成逐行文本，便于贴进日志核对。两者只做投影，不重算任何数值，`simulationReady` 仍是 `false`。

## 10. 录入一份新数据的步骤

1. 从版本化数据抄录动作：`id`、`actorId`、`kind`、`timing`、`hits`（含 `scaling` 与 `triggerIds`）、产球、能量与冷却。
2. 把 `triggerIds` 引用的效果写进 `effects`：面板增量或敌人减益、持续帧数、叠层策略。
3. 填 `gameVersion` 与 `source`，写清抄录版本与出处；没有出处的数据不要进仓库。
4. 跑 `validateDataPack`，把问题清零。
5. 写一条轴：档位、测量窗口、步骤、每个角色的初始能量。
6. 跑 `simulateTeam`，看 `checks` 停在哪个 stage。
7. 若是回归用数据，放到 `test/fixtures/team-sim/` 并在套件里加断言。

## 11. 已知限制

- 数据包与面板的版本一致性已在校验里强制（`versions` 关），但仓库里除示例包外没有**真实**版本的数据，跨版本共存的实际风险还没被真实数据验证过。
- 响应型只改动作时长；命中偏移与取消窗口仍按帧给定，不随档位重算。
- 卡肉只按数据里给的帧数冻结，未做实测校准；冻结期间的画面表现（动作变慢、镜头停顿）不建模，只把时钟与后续排期顺延。
- 附着与反应、多目标都未建模。
- 效果表只支持「数据声明、命中触发」这一种来源：没有条件判断（生命阈值、层数消耗、随机概率），也没有附着与反应；触发一次只按声明施加，不回溯改写已经结算过的伤害。
- 机制层只建模纯岩试点四个角色，并且只认 `scheduler: 'fixed'`；`asap-sequence` 轴与 `wait` 步骤会被拒（见第 3 节）。
- 机制标记由数据声明，内核**不校验主人身份**：标记挂在谁的动作上，就按谁的机制结算。录入时必须自己保证只有主人能挂自己的标记，否则等于给了任意动作一个免费增益。
- 一斗 Q 期间的「NA1/NA3 给层」只记成检查项提示，不改层数消耗逻辑；召唤物命中不进事件队列，由结算层按施放点 + 间隔展开。
- 仓库里没有官方帧表：P1 夹具的动作帧数是占位值，包 `source` 里必须写明；机制时长来自天赋描述（10 级），未经实测校准，结果一律带近似项。

## 12. 队伍 DPS 标准（固定，不允许更改）

口径写死在 `src/modules/teamSimulation/dpsStandard.ts` 的 `DPS_STANDARD` 里，只能引用、不能覆盖：

| 项 | 值 |
|---|---|
| 目标 | `TARGET_PRESETS['ruin-guard-lv110']`：110 级遗迹守卫（小宝） |
| 抗性 | 10%（`resistance = 0.1`） |
| 窗口 | 120 秒现实时间 |
| 开局能量 | 0，且必须**显式**写 0 |

- 窗口换档位不换秒数：`dpsWindowFrames(tier) = round(120 × tier.fps)`（60 档 7243 帧、56 档 6758 帧、625 档 79889 帧）。要换档位就跑标准给的帧数，不要手写别的数。
- `checkDpsStandard({ frameTier, targetPresetId, measurementEndFrame, actors })` 返回违规列表，空数组才算合格；它只看这四项，不替你猜别的东西。
- 分母用现实秒：评分 `= 窗口内总伤害 / 120`。卡肉冻结期间现实仍在走表，磨得慢就该在分数上吃亏。
- 想换目标或换窗口，那就是**另一个口径**，不能再叫 DPS 标准；要改标准本身，得同时改 `dpsStandard.ts`、本表与 `test/team-sim-dps-standard.test.mjs`。

## 13. 录制端（脚本录制）

`scripts/record-keys.py` 是录制端，只负责把「按键 + 单调时钟毫秒」落成 `RecordingV1`；依赖 `pynput` 需自行安装，仓库不分发运行环境，也不在运行时调用它。

```bash
python -m pip install pynput
python scripts/record-keys.py --list-tiers
python scripts/record-keys.py --tier fps-60 --game-version 7.1 --keymap-version gs-default-1 \
    --actors itto,gorou,albedo,zhongli --active itto --source record-keys.py@you --out out/recording.json
python scripts/record-keys.py --selftest --tier fps-60 --game-version 7.1 --keymap-version gs-default-1 --source s@t
```

- F1 开始（同时是起手标记）、F2 结束并写文件；时间戳在按键回调里立即取，只用 `time.monotonic()`。
- 档位 / 键位表版本 / 游戏版本 / 录制者四项缺一即拒；未知档位直接拒绝并列出合法值。
- `--selftest` 不接键盘，用假时钟验证序列化与契约（无外设/CI 环境用）。
## 14. 归因与验收（P2 前准备）

### 14.1 在场覆盖：只回答「谁在场」

- `TimelineHit.activeEffects`：这一发结算时（快照早于本发携带的触发）仍生效的效果 id，按字典序。
- `DamageRow.effects`：结算层把效果 id 与机制窗口**来源名**（如 `gorou-e`）合并去重后的 id 列表，召唤物命中同样带。
- `TeamRunReport.effectUsage`：按 id 汇总「在场时打出的命中数与伤害合计」，摘要行以「在场覆盖：」开头。

这三个字段只说明谁在场，**不说明谁贡献了多少伤害**。连续乘区下把总伤按来源拆账需要反事实重算（逐个撤掉来源再跑一遍），P1 不做；要报「某 buff 提升了 X」必须另立接口并注明算法。

### 14.2 黄金集与误差指标

`src/modules/teamSimulation/metrics.ts` 只做算术，不提供期望值、不读文件、不跑模拟。

```ts
interface GoldenCase {
  id: string
  source: string            // 期望值来源：录像、手算稿、对照实现与版本；空来源整条无效
  kind: 'measured' | 'hand-calculated' | 'cross-check' | 'synthetic'
  expected: { total: number; perActor?: Record<string, number> }
  tolerance?: number        // 单例容差，缺省 20%
}
```

- `validateGoldenCases(cases)` 拒绝：缺 id、重复 id、缺来源、未知 `kind`、期望总伤非正、容差为负。
- `evaluateGolden(cases, actuals, thresholds?)` 输出每条的相对误差、分角色贡献偏差（百分比份额的最大差值）、以及闸门结论：
  - `synthetic` 只展示、**不计入闸门**（它是占位数据）；
  - 没有实跑结果的用例记 `missing`，不按 0 参与统计；
  - 计入闸门的样本 ≥3 条时看中位数（默认 10%），<3 条只看单例容差（默认 20%）；任何一条超容差或贡献偏差 >10pp 即 `fail`；
  - 一条可计入的都没有时报 `insufficient-data`，而不是「通过」。
- 阈值默认值在 `GOLDEN_THRESHOLDS`，按 `docs/队伍模拟-P1纯岩试点设计.md` 的验收口径调整时改一处即可。其中 `dpsMedian` 目前**没有**被 `evaluateGolden` 使用：比较 DPS 误差要先把不同窗口归一化，P1 只比总伤，这条留给窗口不一致的对比场景。
- 现在仓库里**没有一条实测黄金用例**，所以闸门恒为 `insufficient-data`；这是事实状态，不要用合成数据把它刷成 `pass`。

## 15. 元素反应（P2）

命中上写 `reaction: { kind, aura }`，由数据声明这一发命中时目标身上的附着；引擎只校验元素配对，不做附着量、衰减与 ICD。

- `kind` 只接受：`vaporize`、`melt`、`aggravate`、`spread`、`overloaded`、`electro-charged`、`superconduct`、`swirl`、`bloom`、`burning`。
- `aura` 是命中瞬间目标身上的附着元素（七元素之一）；方向由 `element`（触发元素）与 `aura` 共同决定：
  - 蒸发：水打火 2.0、火打水 1.5；融化：火打冰 2.0、冰打火 1.5
  - 超激化：雷打草 1.15；蔓激化：草打雷 1.25
- 剧变倍率：超载 2.75、感电 2.0、超导 1.5、扩散 0.6、绽放 2.0、燃烧 0.25。
- 等级系数 `REACTION_COEFFICIENT` 取自 miao `eleBaseDmg` × 4（与社区等级系数表逐项一致）：1～90 级连续，91/92/93/94/96～99 在原始表里就缺——角色最高 90 级，不影响结算。
- 增幅：`伤害 = 直伤 × 反应倍率 × (1 + 2.78 × EM / (EM + 1400))`，乘在基础伤害区。
- 激化：`基础伤害 += 反应比例 × 等级系数 × (1 + 5 × EM / (EM + 1200))`，加在基础伤害区。
- 剧变：`伤害 = 等级系数 × 反应倍率 × (1 + 16 × EM / (EM + 2000))`，只乘抗性区，不吃防御、增伤与暴击，结果里单独成一行（`origin: 'reaction'`）。
- 精通取角色面板的 `mastery`；数据包不单独传精通。
- 拒绝：状态型反应（碎冰要冻结、烈绽放/超绽放要草原核、结晶无伤害、冻结是状态）→ `unsupported`；配对不符 → `invalid`；物理命中写反应 → `invalid`；等级不在表内 → `unsupported`。

### 15.1 月反应与星烁（P3）

命中上的 `reaction` 也可以声明 `lunar-*` / `stellar-*`，额外字段（都可省略，省略即用官方默认）：

| 字段 | 含义 | 缺省 |
|---|---|---|
| `talent` | 是否吃到「月曜反应伤害提升」这类天赋倍率 | `false` |
| `count` | 星超导/星辉冰旋的叠层计数 | 星超导 12，星辉冰旋 6 |
| `fypct` | 专用反应加成，乘在等级系数上 | 0 |
| `fyplus` | 固定加值 | 0 |
| `elevated` | 提升乘区 | 0 |
| `kNum` | 反应系数乘区 | 1 |

倍率：月绽放 1、月感电 3（`talent` 时 7.2）、月结晶 1.6（`talent` 时 3.84）；星扩散 1（`talent` 时 3）；星超导查 13 项计数表 `[1, 1.45, …, 2.0]`；星辉冰旋计数 ≥3 时为 12、否则 8。

精通曲线与剧变不同：`1 + 6×EM/(EM+2000)`（剧变是 16）。

结算：

```text
(等级系数 × (1+fypct) × 倍率 × 精通系数 + fyplus) × (1+elevated) × kNum × 暴击 × 抗性区
```

暴击是显式乘区 `1 + cpct × cdmg`（`canCrit` 为 false 时不乘），这一点与普通剧变不同。月反应与星烁**单独成段**（`origin: 'reaction'`），不是把直伤放大。

拒绝：配对不符 → `invalid`（如 `lunar-charged` 只接受 hydro↔electro）；`count` 非正整数、`kNum` 非正、其余加成负值或非有限 → `invalid`。

#### 计数来源由效果驱动

星超导与星辉冰旋的层数不是静态值：命中上写 `countFrom: '<效果 id>'`，引擎在结算时读该效果当帧的层数（`EffectRuntime.stacksAt`），与直接写 `count` 互斥。效果没登记或已到期时层数为 0，所以数据包校验要求 `countFrom` 必须指向 `effects` 表里的条目——否则整包按 `unsupported` 拒绝，不会静默按 0 层算。

```json
"reaction": { "kind": "stellar-conduct", "aura": "electro", "countFrom": "stellar-stack" }
```

#### 反应加成也能由效果提供

`fypct` / `elevated` / `kNum` 既可以写在命中上，也可以由效果表提供：`EffectSpec.reactionBonus` 是面板与敌人减益之外第三个乘区来源，按加法叠加。数据里的 `kNum` 是乘数，效果里的是加数（最终 `1 + 合计`）。这样换人、叠层、队伍加成都能改反应结算，而不必改动作数据。

```json
"blessing": { "id": "blessing", "target": "team", "durationFrames": 240,
              "reactionBonus": { "fypct": 0.2, "elevated": 0.1, "kNum": 0.5 } }
```

### 14.3 效果贡献（反事实归因）

`attributeEffects(input)` 对效果表里的每一项各跑一轮「去掉它」，差额就是该项的贡献：`delta = baseline - without`。这是反事实口径，不是因果分解——效果互相叠加时，单独去掉一项的差额不等于它在总量里的份额，所以**不给百分比排名**。从未被任何命中触发过的效果差额恒为 0，不会因为表里有它就凭空给贡献；去掉后那一轮跑不起来的效果记进 `skipped`，差额记 0 而不编数字。

```js
const report = attributeEffects({ pack, rotation, members, expected, targetPresetId, crit, debuffs })
// report.rows: [{ effectId, baseline, without, delta, triggers }]，按 delta 降序
```

## 18 录制导入（`RecordingV1` → 轴）

录制的职责只有一个：把「第几毫秒按了哪个键」原样记下来。动作语义、角色、帧号都由导入端按键位表和帧率档位折算，录制文件里不写这些。

```js
import { validateRecording, recordingToRotation } from 'metaelement/teamSimulation'

const checked = validateRecording(rawRecording)
if (checked.status !== 'ok') throw new Error(checked.issues.map(i => `${i.path}: ${i.message}`).join('\n'))

const converted = recordingToRotation(checked.recording, keymap, {
  id: 'rotation:recording-001',
  measurementEndFrame: 7243,   // fps-60 档下 120 秒
}, pack)                          // 传 pack 时会顺带跑 validateRotation
if (converted.status !== 'ok') throw new Error(converted.issues.map(i => `${i.path}: ${i.message}`).join('\n'))
```

- **只认按下**：`down` 生成步骤，`up` 只用来检查录制完整性（至少一次按下、时间戳单调不减）。
- **帧号**：`frame = round(atMs / (1000 / fps))`。同一段按键换档位会得到不同帧号，所以录制必须带 `frameTierId`。
- **键位表**：`{ version, bindings }`，值与录制里的 `keymapVersion` 必须一致；`{ actorId, switch: true }` 生成换人步骤，`{ actorId, actionId }` 生成动作步骤。
- **四项元数据**（`frameTierId`/`keymapVersion`/`gameVersion`/`source`）缺一不可：缺了就无法判断这段按键是哪套键位、哪个版本录的。
- **窗口**：`measurementEndFrame` 必须大于最后一步的帧号，否则最后一段动作不会被结算——这类错误在导入时直接拒，不留到结算后再解释。

## 19 发布闸门

`evaluateReleaseGate({ result, golden, reactions, minimumCases })` 把「能不能对外说这是结果」拆成六关，**任意一关被拦即 `blocked`**：

| 关 | 通过条件 | 不通过的含义 |
|---|---|---|
| `run` | 本轮 `status === 'calculated'` | 没有可发布的结算结果 |
| `mode` | `mode === 'dps-standard'` | 诊断口径的目标/窗口/起手能量都不是标准值 |
| `accuracy` | `timeline.accuracy === 'verified'` 且无 `approximateItems` | 还有未校准的近似项 |
| `reactions` | 用到的反应家族都有 fixture | 该类反应还没有可对照的 fixture |
| `resources` | `plan.checks` 无 `violation` | 机制资源检查发现违规 |
| `golden` | 黄金集 ≥10 例且 `evaluateGolden().gate === 'pass'` | 用例不够给 `insufficient-data`，超差给 `blocked` |

三态语义不同，不要混用：`pass` 才可对外；`insufficient-data` 是**证据不够**（不是结果错了）；`blocked` 是**有硬条件不成立**。`formatReleaseGate(verdict)` 给出逐关明细与阻断项。

## 20 卡肉（hitlag）

依据：NGA《简明卡肉学》与 Fandom `Hitlag/Data`（2026-11-01 取），两者数据一致。卡肉有四个参数，本仓库只用前三个：

| 参数 | 含义 | 本仓库用法 |
|---|---|---|
| 初始停滞时间 `HitlagTime` | 该次攻击的基础卡肉时长 | 按动作取值，见下表 |
| 停滞期间时间流速 `HitlagTimeScale` | 停顿期间时间仍在缓慢流动，常见 0.01 | 固定按 0.01 计入 |
| 韧性影响 `Poise-Extendable` | 目标韧性正常时额外 +0.06s；韧性被破坏则不加 | 目标为不破韧的桩，按「正常韧性」算 |
| 部署可见 `Deployable` | 是否只对受击方生效 | 不建模（不影响时长） |

**换算公式**（文章给出的算例逐位对得上）：

```
实际延长 = (HitlagTime + 0.06) × (1 − 0.01)       // 韧性正常、时间流速 0.01
帧数     = ceil(实际延长 × 60)                    // 帧数向上取整，这是全局规则
```

**已写进数据包**（`test/fixtures/team-sim/geo-four-pack.json`，一斗普攻）：

| 动作 | HitlagTime | 实际延长 | 帧 |
|---|---|---|---|
| 普攻 1、2 | 0.08 s | 0.1386 s | 9 |
| 普攻 3、4 | 0.10 s | 0.1584 s | 10 |

卡肉冻结游戏时钟，所以**固定调度必须把卡肉帧算进去**：同一份轴加卡肉前「41 帧接第二段」合法，加卡肉后最早可取消帧变成 50。按段累加后的起手帧 0 / 50 / 110 / 177，命中帧 **23 / 75 / 126 / 225**。

其余动作暂未写：表中的分武器通用行（单手剑普攻 0.03、双手剑重击挥舞 0.03、终结 0.15、弓瞄准命中要害 0.12、法器 0 等）还没有对应到具体动作数据；五郎的弓普攻为 0，因此不写。技能与爆发的卡肉在文章里只零散出现（如荒泷一斗元素战技 0.02s、钟离重击 0.06s），尚未逐条核对进数据包。

## 21 元素附着与 ICD

依据：《元素附着论》（第三版）与 biligame wiki 角色数据。

- **默认规则**：同一套冷却下，第 1、4、7… 次计数命中附着，其余计数不附着；计数从第一次命中起 2.5 秒后重置。
- **标签与组别**：无标签 = 不参与附着冷却；同标签且同组别 = 共用一套冷却；异标签或异组别 = 各算各的。
- **计数规则**：一次伤害 = 一次计数；一段多击的每个伤害数字各加 1；召唤物（岩脊共鸣、雨帘剑等）的命中同样计数。
- **卡肉不延长附着冷却的计时**（游戏暂停才会）。
- 剧变反应的伤害冷却（超导/碎冰/扩散 0.5s 内 2 次；超载/感电 0.5s 内 1 次）与公共冷却（碎冰 0.2s，其余 0.1s）尚未建模。

**尚未接入**：逐段附着量与组别需要 wiki 的 `元素附着论/角色数据` 页（包含每个角色每段的元素量与 ICD 标签），本轮未取到，因此 `HitSpec` 还没有 `aura`/`icd` 字段。

## 22 入口传播与条件效果契约

- 顺序轴按顶层 `frameTierId` 换算动作包，录制轴按已声明的 `recording.frameTierId` 换算，随后由原有录制校验器校验。换档后的动作时长必须容纳全部非延迟命中和产球事件，延迟事件继续使用原有独立时点。
- `simulateTeam` 缺省月相表示队伍没有月兆角色，传给时间线的显式值为 `none`。低层时间线和效果 API 未传月相时仍沿用既有 `initial` 默认值。`requiresMoonPhase` 继续只接受 `initial` 或 `full`。
- 海染泡沫只收集效果装备者的治疗。泡沫一旦形成，后续动作取消继续只影响可取消的普通动作事件，泡沫按自己的生成时点和有效期结算。
- 动态元素减抗、元素加伤和队伍人数加成与效果运行时使用相同叠层和刷新状态。同一效果的不同元素分别保留有效期，独立效果来源仍按原有规则叠加。
