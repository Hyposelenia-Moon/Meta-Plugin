# 队伍模拟 P1 纯岩试点设计

> 性质：**只读设计**。本文只描述契约、时间模型、状态模型、数据需求与验收方式，不含实现，也不含任何 DPS、秒数或循环长度结论。
> 依据：`docs/队伍模拟-P0底座.md`（已落地的 P0 边界）、`Meta-队伍伤害重构方案探索-2026-10-30.md` 的 §6、§7、§8.4–8.5、§9、§11、§12。
> 本文出现的机制数值一律以游戏内描述与版本化数据包为准；文中不写具体百分比，避免把未验收的数字当成契约。

## 1. 范围

- 队伍：C0 一斗 / 五郎 / 阿贝多 / 钟离，单目标静止、无初始光环、无来袭。
- 目标：`TARGET_PRESETS['dummy-lv100']`（P0 已定义：Lv.100、标准防御、各元素与物理抗性 10%、无限血、静止、无敌方护盾/相位）。
- 输入资格：只接受**可重建的原始配装**（P0 的 `CharacterBuild` + `provenance`）。只有最终面板的输入在 P0 已被 `panelCheck` 拒绝，P1 维持该拒绝。
- 明确不做：元素反应与月反应/星烁、多目标、走位与碰撞、来袭伤害、敌方护盾/相位、卡肉校准、首批清单之外的武器/套装/命座。
- 纯岩队打无光环目标不产生结晶；若目标带元素，战斗条件就变了，不属于本试点。

## 2. 与 P0 的边界

| 项 | P0 现状 | P1 处理 |
|---|---|---|
| `adaptMiaoAvatar` / `readTeamBuilds` | 已落地，产出 `CharacterBuild` | 直接复用，不改读取规则 |
| `validateCharacterBuild` | 已落地，契约层把关 | 复用；P1 新增字段走同一套 `Issue` |
| `buildPermanentStats` | 已落地，只出静态面板 | 复用，**不扩展**成运行时状态；P1 在它之上维护可变状态 |
| `calculateOrdinaryHit` | 已落地，普通直伤单 hit | 复用为伤害乘区，不承载触发与时间 |
| `TARGET_PRESETS` | 已落地 `dummy-lv100` | 复用；新增 `placementScenarioId` 引用情景 |
| `legacyEstimate` | 已落地，类型占位 | 继续只做兼容模式出口，不混入 P1 结果 |
| 来源 id 格式 | `character:<id>:a<突破>` 等 | 复用同一格式登记 buff 来源 |

P1 不改变 P0 任何已验收行为；新增能力全部落在新模块，靠类型与测试隔离。

## 3. 新增契约（草案）

草案用于讨论与评审，字段名与粒度在实现前可调整；一旦进入实现，必须与测试断言同步冻结。

```ts
type Frame = number // 相对测量起点的整数帧

interface ActionSpec {
  id: string // 例如 itto.normal-1、gorou.skill
  actorId: string
  kind: 'normal' | 'charged' | 'plunge' | 'skill' | 'burst' | 'switch' | 'combo'
  /**
   * 动作时长口径，二选一，数据必须显式声明：
   * - `{ type: 'frames', frames }`（计时器型）：帧号与档位无关；
   * - `{ type: 'response', k, bMs }`（响应型）：现实时长 = k × 帧生成时间 + bMs，按档位向上取整成帧。
   * 未验收帧表时不得填估算值。
   */
  timing: { type: 'frames'; frames: Frame } | { type: 'response'; k: number; bMs: number }
  hits: HitSpec[]
  /** 可取消窗口，决定 ASAP 调度能多早接下一步 */
  cancelWindows?: { fromFrame: Frame; toFrame: Frame }[]
  cost?: { energy?: number }
  cooldownId?: string
  /** 状态门槛：层数、能量、前台、武器/命座要求 */
  requires?: string[]
}

interface HitSpec {
  atFrame: Frame
  motionValue: number // 倍率，来源必须是版本化数据
  element: 'geo' | 'physical'
  canCrit: boolean
  /** 命中后触发的效果 id，由规则表解析，不在数据里写死顺序 */
  onHit?: string[]
}

interface EffectSpec {
  id: string
  source: string // character:<id>:a<n> / constellation:... / artifact-set:...
  scope: 'self' | 'party' | 'enemy'
  stats: Record<string, number>
  duration?: number // 秒；0 表示瞬时
  snapshot: 'snapshot' | 'dynamic'
  conditions?: string[]
}

interface SimulationInput {
  builds: CharacterBuild[] // 四人，P0 契约
  rotation: RotationSpec // 方案 §7.1，P1 只实现最小子集
  target: { presetId: string; placementScenarioId: string }
  randomness: { mode: 'seeded'; seeds: number[] } | { mode: 'expected' }
  bundleId: string
}

interface SimulationResult {
  status: 'simulated' | 'unsupported' | 'invalid'
  /** 只对已验收轴为 true；草案轴与卡肉未校准场景必须为 false */
  simulationReady: boolean
  accuracy: 'verified' | 'approximate'
  approximateItems: string[] // 逐条列出被省略或未校准的机制
  hits: { frame: Frame; actorId: string; actionId: string; damage: number; crit: boolean }[]
  resources: { actorId: string; energy: number; legal: boolean }[]
  coverage: Coverage[]
  issues: Issue[]
}
```

约定：
- `simulationReady` 只在「输入可重建 + 机制全部登记 + 帧表已验收 + 无未校准近似项」时为 `true`；任一不满足就 `false` 并写 `approximateItems`。
- 结果里的 `hits` 是逐 hit 事件，不做预聚合；窗口与贡献由聚合层从事件流算，避免两套算法。
- 任何未知机制不得补 0 或补 1，只能登记为 unsupported 或明确列入 `approximateItems`。

## 4. 时间模型

- 事件键 `(frame, phase, sequence)`。同一帧的相位顺序由机制规则表决定，**禁止用角色 id 排序代替游戏顺序**；未查清且会改变结果的同帧先后，记录歧义并拒绝严格结论。
- 帧率档位 `frameTier` **必填、不设默认**：`fps` 决定一帧的现实毫秒数（1000/fps），`timerTickMs = round(1000/fps)` 决定游戏计时器每帧推进的整数毫秒。技能文本里的「一秒」是游戏时间，对应现实秒数 = `(1000/fps) / timerTickMs`，即《原神帧率学》里的「计时器时间」：小于 1 叫快帧，大于 1 叫慢帧。同一段帧序列换档位后帧号不变、毫秒不同，所以档位是输入而不是注解。
- 动作生命周期：请求 → 能力检查（前台/能量/CD/状态）→ 扣费与起 CD → 施放时快照 → 调度 hit 与状态事件。
- 调度器只实现两种：`fixed`（帧号必须成立，否则报失败帧与原因）与 `asap-sequence`（尽早执行，报告实际时长与等待）。ASAP 不是自动优化轴，等待超截止仍算失败。
- 动作占用、可取消窗口、切人冷却、体力、充能次数分开检查；后台协同只按真实触发条件入队，不按前台 hit 数复制。
- 卡肉：P1 **不建模**。所有受卡肉影响的时钟（时长、窗口内 hit 数、buff 到期）都必须标进 `approximateItems`，此时 `accuracy='approximate'`。

## 5. 状态模型

| 层 | 内容 | 说明 |
|---|---|---|
| 队伍 | 前台角色、岩角色数、组队共鸣 | 岩人数影响五郎增益分档，必须可回放 |
| 角色 | 面板属性、运行时 buff、能量、CD、命座、天赋等级 | 静态部分来自 P0，运行时部分只由事件改变 |
| 特殊资源 | 一斗层数、五郎战旗、阿贝多阳华、钟离护盾与柱 | 每个资源单独的生成/消耗/到期规则 |
| 目标 | 等级、抗性、防御、减抗与减防累计 | 减防上限 0.9、负抗不截断沿用 P0 |
| 能量 | 粒子生成 → 飞行 → 吸收 | 同色/异色、收取者、前后台、充能效率分别记录 |
| 输出 | 逐 hit 伤害与触发记录 | 与 P0 的 `OrdinaryDamageResult` 保持同口径 |

快照只捕获指定依赖：某技能快照不等于该角色全部属性冻结；敌抗、防御与部分直接效果仍动态。

## 6. 四角色机制拆解

只列形态与需要建模的状态，不写数值。数值全部进版本化数据包。

### 一斗

- 关键状态：层数（0–5）、爆发状态（攻击力转化、普攻/重击转岩、攻速变化）。
- 需要建模：普攻分段与层数获取、消耗层数的重击序列、E 的召唤物与受击/到期触发、Q 的施放与到期、Q 期间普攻命中获层。
- 快照：Q 的属性转化是运行时计算，不是静态快照；E 召唤物的伤害按规则决定是否快照。
- 随机性：无（首批 C0，不涉及暴击触发的装备）。
- fixture：单轴命中序列（层数增减与重击次数）、Q 到期后属性回落。

### 五郎

- 关键状态：战旗存在、战旗跟随（E 固定 / Q 随动）、队伍岩角色数决定增益档位。
- 需要建模：E 的领域生成与分档增益、Q 的随动战旗与周期效果、增益的到期与范围条件。
- 快照：分档增益按施放时点判定，切人/岩人数变化是否重算需按规则写清楚，不能默认实时重算。
- 随机性：无。
- fixture：分档断言（岩人数变化 → 增益档位）、覆盖时间。

### 阿贝多

- 关键状态：阳华存在、触发 ICD、Q 的花数。
- 需要建模：E 的施放与范围、由队友/自身命中触发的阳华伤害、Q 的爆发与花、快照口径。
- 快照：阳华伤害基于施放时面板（需数据与规则共同确认），Q 结束后的队伍增益单独登记。
- 随机性：产球按概率，走 `randomness` 回放，不用平均产球断言能量足够。
- fixture：触发次数与 ICD 断言、快照差异（五郎 E 先后顺序对阳华伤害的影响）、种子回放一致性。

### 钟离

- 关键状态：护盾存在与失效、柱存在、减抗范围与持续时间。
- 需要建模：E 长按的护盾生成、柱子生成、Q 的伤害与石化（P1 目标静止，**石化不建模**，列入近似项）、减抗的生效与到期。
- 快照：护盾按施放时面板结算；P1 无来袭伤害，护盾不被打破，但结果必须声明这是条件假设而非实战常态。
- 随机性：无。
- fixture：减抗窗口与目标抗性变化、护盾存在标记。

## 7. 数据需求清单

| 数据 | 用途 | 来源要求 |
|---|---|---|
| 动作帧表（逐 hit 帧、可取消窗口、动作总帧） | 时间线 | 合格录像逐动作抄录或自建并验收；不接受估算 |
| 倍率表 | 伤害 | 游戏内天赋/武器描述 + 版本号 |
| 技能/命座/武器/套装效果 | 触发与属性 | 首批清单逐条登记，缺一条就不进正式模拟 |
| 产球与能量 | 资源合法性 | 每技能的产球数量与类型；随机部分按种子 |
| 天赋等级与命座 | 面板与效果 | 输入中显式给出，P1 限 C0 |
| 目标与情景 | 抗性/减防/覆盖 | `dummy-lv100` + `placementScenarioId` |

缺任一必需数据时：拒绝轴（`status:'invalid'` 或对应 `unsupported`），不得用默认值补齐。

## 8. 随机性与确定性

- 暴击策略与随机源分离：伤害可取期望，但依赖暴击的触发（如西风类武器产球）必须实际轨迹或固定种子；**首批排除西风类武器**，缩小支持集而不是伪造能量。
- 阿贝多随机产球等按种子回放；结果保留全部预先声明的种子，任一严格轴分支非法就整体标为轴不可保证执行，并给出失败诊断，不丢弃失败种子。
- 同一输入、数据包、种子列表必须产出相同日志；升级后留差异报告。

## 9. 验收方式

P1 退出条件的可执行拆解：

1. **单角色四轴**：每个角色一条最小轴，断言的是事件轨迹（hit 数、帧、CD、资源、层数），不是 DPS。
2. **双人交互三组**：
   - 五郎 E 先/后于阿贝多 E，检验阳华快照口径；
   - 钟离减抗 × 一斗 Q 窗口，检验抗性乘区与到期；
   - 岩人数分档（换人后增益档位变化）。
3. **四人三轴**：持续轴、爆发轴、速切轴，草案状态 `draft-unvalidated`；三轴必须在总伤、时长、贡献、buff 覆盖中至少两项有可解释差异（纯岩反应数同为零是正确结果）。
4. **确定性**：同输入同种子重跑，逐事件日志一致。
5. **近似项清单**：卡肉、石化、结晶、多目标必须出现在 `approximateItems`，缺一项视为结果不可用。

精度门槛不在 P1 内：需要至少 10 个合格实测场景与覆盖配额，P1 只交付结构与事件级正确性。

## 10. 实施顺序

只排依赖，不估工期：

1. 契约与 Schema（`RotationSpec`/`ActionSpec` 等）与校验，不产生模拟结果；
2. 时间内核与事件队列，用无角色的合成事件测确定性；
3. 一斗单人轴（层数、Q 转化）→ 五郎 → 阿贝多 → 钟离；
4. 双人交互 → 四人三轴；
5. 结果区、日志、文档与覆盖表。

## 12. 已落地：时间内核与 Schema（2026-11-01）

已实现 `src/modules/teamSimulation/timeline.ts`，只用合成动作夹具验证语法与语义，**不含任何游戏帧表数值**：

- `FRAME_RATE = 60` 只作为数据编帧的标称帧率；实际时长换算由必填的 `frameTier` 决定。
- `FrameTier { id, fps, timerTickMs, source }` 与 `FRAME_TIERS`：从《原神帧率学》计时器型帧率档位表（BV1Z8rLBGEeo）抄录 8 个档位（56/60/64/73/104/217/384/625），`timerTickMs = round(1000/fps)`。表里第一列是解锁插件里输入的帧数（现称芙芙启动器帧数），不是游戏内常量；只收实测值，不插值。
- `validateFrameTier`：缺省 → `missing`；空 id、非正帧率、非正整数 tick → `invalid`；`timerTickMs ≠ round(1000/fps)` → `invalid` 并点出应有的取整值。
- 结果新增 `timing`：`tierId`、`fps`、`timerTickMs`、`gameMsPerFrame`、`realMsPerFrame`、`timerSecondsPerGameSecond`、`gameMs`、`realMs`、`assumptions:['constant-frame-rate']`。现实时长 = 帧 × 1000/fps，游戏时长 = 帧 × timerTickMs；`timerSecondsPerGameSecond < 1` 是快帧，`> 1` 是慢帧。
- 两种时长口径（`ActionSpec.timing`，必填、不设默认）：
  - 计时器型 `{ type: 'frames', frames }`：帧号与档位无关，换档位只换毫秒。
  - 响应型 `{ type: 'response', k, bMs }`：`现实时长 = k × 帧生成时间 + bMs`，再按当前档位 `Math.ceil(现实时长 / 帧生成时间)` 折算成整数帧——同一动作换档位帧数会变，这是《原神帧率学》里响应型曲线的来源。
  - `resolveActionTiming(timing, tier)` 负责折算；`validateActionSpec` 只做结构校验（缺字段、负系数、k 与 bMs 同时为 0、未知口径），响应型的帧上界要等档位给定后才在 `simulateTimeline` 里判，越界会点名档位与折算帧数。
  - 命中偏移与取消窗口仍由数据给定，两种口径共用；响应型只改变动作结束帧，不代表命中时刻也跟着档位精确重算。
- `EVENT_PHASES` 固定同帧结算骨架（起手 → 扣费 → 快照 → 命中 → 伤害 → 触发 → 回能 → 状态）。
- 数据契约：`ActionSpec`（`timing` 时长口径、`hits[].atFrame`、取消窗口、产球、能量消耗、冷却、门槛标记、卡肉帧）、`TimelineInput`（`fixed` / `asap-sequence` 两种调度、测量窗口、切人帧、充能效率、状态标记）。
- `validateActionSpec` 拒绝小数帧、越界命中帧、乱序命中、反向取消窗口、非正产球数量；帧一律整数，不做四舍五入。
- `simulateTimeline` 产出 `(frame, phase, sequence)` 事件日志、命中列表、角色能量与冷却、每次请求的请求帧/实际帧；同帧先结算已发生命中再起新动作；取消窗口内接新动作会裁掉上一动作未发生的命中与收尾。
- 冷却从起手帧开始计；产球在 `起手 + atFrame + travelFrames` 到达并乘以充能效率；能量不足或冷却未好时，`fixed` 报失败帧，`asap-sequence` 等到可用帧并在 `requests` 里记录等待。
- `simulationReady` 恒为 `false`；含卡肉数据的动作把结果标成 `approximate` 并写入 `approximateItems`（内核不延长时钟，卡肉未校准）。
- 回归：`test/team-sim-timeline.test.mjs`（合成动作、固定帧断言、档位切换与档位校验负例、响应型折算与换档位越界负例、确定性对比）。示例：同一个 36 帧动作，60 档结束于 24 帧 = 408ms 游戏时间，56 档 = 432ms；响应型 `k=10, bMs=100` 的动作在 60 档折 17 帧、56 档 16 帧、625 档 77 帧。
- 命中结算：`src/modules/teamSimulation/hitDamage.ts` 的 `calculateTimelineDamage({ timeline, contexts })` 把 `timeline.hits` 逐段映射成 `OrdinaryHit` 后调用 `calculateOrdinaryHit`，产出 `total`、`rows`、`perActor`、`target`，`simulationReady` 恒为 `false`。`contexts` 以 `actorId` 为键：四人队每人的面板分开取，同一轮内版本、来源、目标口径与减益必须一致，否则拒绝汇总。
- 结算属性必须显式：`HitSpec.scaling` 是 `atk` / `hp` / `def` 之一，倍率乘哪一项面板由数据声明；缺省报 `missing`，未知值报 `unsupported`。
- 加成取法：岩/元素命中读 `stats.dmg + stats[element]`，物理命中只读 `stats.phy`；暴击取 `stats.cpct` 与 `stats.cdmg`，目标等级与抗性只从 `TARGET_PRESETS` 取，不由调用方自报。
- 队伍减益 `debuffs`（`defenseReduction` / `defenseIgnore` / `resistanceReduction`）必须显式给值，P1 一律传 0；传非 0 直接 `unsupported`，因为钟离护盾减抗还没建模。
- 回归：`test/team-sim-timeline.test.mjs` 与 `test/team-sim-hit-damage.test.mjs`（每段伤害与直接调公式逐项相等、换元素换加成键、目标/减益/面板拒绝项）。
- 数据包：`src/modules/teamSimulation/dataPack.ts` 的 `validateDataPack({ schemaVersion: 1, gameVersion, source, actions })` 校验版本（非 1 → `version-mismatch`）、版本与出处非空、动作表非空、动作 `id` 必须等于键，再逐条走 `validateActionSpec`；纯函数、零 I/O，缺什么就拒绝，不拿默认数据补。
- 轴：`src/modules/teamSimulation/rotation.ts` 的 `RotationSpec`（`id`、`scheduler`、`frameTier`、`measurementEndFrame`、`steps`、`actors`、`activeActorId`、可选 `switchFrames` / `energyRecharge` / `stateFlags`）与 `validateRotation(spec, pack)` 拒绝：未知动作、未知步骤类型、非法帧率档位、非正窗口、角色重复、初始能量越界、初始前台不在角色表。
- 编排：`src/modules/teamSimulation/teamRun.ts` 的 `simulateTeam({ pack, rotation, members, expected, targetPresetId, crit, debuffs })` 串联「数据包 → 轴 → 每个成员的 `validateCharacterBuild` + `buildPermanentStats` → `simulateTimeline` → `calculateTimelineDamage`」；结果带 `checks`（每关 `stage` / `status` / `issues`），任一关不过就整轮拒绝、不再往下跑；`simulationReady` 恒为 `false`。
- 回归补充：`test/team-sim-pack.test.mjs`（包与轴的拒绝项）、`test/team-sim-team-run.test.mjs`（两角色端到端，每段伤害与直接调公式一致，缺成员 / 缺动作 / 三元组不符都在 `checks` 里点名）；全量 **72/72**。

未落地：真实帧表、卡肉延长、附着与反应、响应型动作模型只做了时长口径（命中时刻仍由数据按帧给定，尚未按响应型重算）、队伍 buff 与减抗、多目标与切人资源消耗。数据包与轴只定义「数据给出后怎么跑」，包里的帧表与倍率数值必须来自版本化数据包，内核不猜、不补默认值。

## 13. 许可与来源

本设计不复制 gcsim 的代码或数据（其自 2026-09-19 起为 AGPLv3）；如需参考其机制表，只作为人工核对线索，落地数据须来自自有抄录与版本化数据包。
