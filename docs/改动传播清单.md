# 改动传播清单


> **任何内容变更都必须同时更新全部消费者并跑固定验收集，不得只改一处。**
> 用户说过"改了什么"，就要把所有对应栏目一起改到位 —— 不要等用户自己查、自己提醒。

## D. 正文要求（提交信息与 PR 正文**同一条规则**，用户定稿）

提交信息（也是 PR 正文的来源）格式：

```
<类型>: <中文简述>

- <要点>
- <要点>
```

- **PR 正文 = 各提交 `- ` 要点的拼接**：按提交顺序（旧→新），重复的合并成一条，**不带提交标题**
  （标题只用于提交本身与 PR 标题）
- 自查：`git log --reverse --format=%B <base>..HEAD`，抽其中的 `- ` 行即为正文
- 没有 `- ` 要点说明提交信息不完整，先 `git commit --amend` 补齐

书写要求：

1. **书面语**：不使用口语与网络语，不使用情绪化表达
   （避免「弄 / 搞 / 炸 / 跑一遍 / 顺手 / 白做 / 就是这么」这类写法）
2. **不用 emoji、不用感叹号**，句末不加标点
3. **不用第一人称**（我 / 咱们 / 我们），主语是改动本身
4. 标题一句话说清"改了什么"，不超过 50 字；正文每条只写一个改动点，写"改了什么 + 为什么或影响"
5. 术语用仓库既有词：主文档 / 标记版 / 网页版（`guide.html`）/ 文档版（`guide.md`）/
   编辑器 / 面板 / 数据仓库 / 攻略页面
6. 文件路径、函数名、提交号、尺寸与字号等标识用反引号包裹，照抄原文
7. 类型前缀沿用仓库既有风格：`feat` / `fix` / `docs` / `test` / `refactor` / `chore`，
   或本仓库专用范围（`data` / `editor` / `display` / `docx` / `web`），例：`data: 归一主词条括注写法`

> 提交由用户本人执行；脚本与自动化只负责准备改动与文案，不代替提交。

其他协作者跑不了这一步）：
