## 一、总体判断

P0 底座对应方案 §12 的 **P0 阶段**（原始配装适配、manifest/来源、单位、永久面板、纯公式、legacy 隔离），已完成其中大部分，但有 7 处契约差异：

| 类别 | 编号 | 是否影响正确性 |
|---|---|---|
| 目录/命名 | D1 | 否，只影响文档一致性 |
| 契约字段缺失 | D2、D3、D5、D6 | 是，缺口可被绕过 |
| 设计空白（方案也未定） | D4、D7 | 否，但影响后续阶段衔接 |

公式与单位口径无分歧：防御分式、减防 0.9 上限、抗性三段、负抗不截断、CR clamp、百分比在入口只规范化一次，均与方案 §8.1 一致；方案 §11.2 的固定算例（同级 0.5、90 对 100 级 190/390、r=−0.2→1.1、CR 0.8/CD 1.6→2.28）与现有测试的冻结值同口径。

## 二、逐项对照

### D1 模块目录

- **方案 §4**：拟 `src/components/team-sim/{types,build,formula}.ts` 与顶层 `src/modules/teamSimulation.ts`；该表自述“拟议位置，尚未创建产品文件”。
- **现状**：`src/modules/teamSimulation/{types,build,formula}.ts`（目录），适配器在 `src/model/TeamBuildAdapter.ts`。
- **建议判定：不采纳方案路径**。实现已经落定并被四套测试覆盖，改路径只有迁移成本没有收益；但方案 §4 的表与本文应各加一句“以实现为准”，避免后来者按方案建第二套目录。
- **已落地**：P0 文档「分层与 API」补了「目录以实现为准」及不采纳理由。

### D2 天赋加成来源（`talents.modifiers`）

- **方案 §5**：`talents: { normal, skill, burst, modifiers: { source, talent, levels }[] }`，注释写明“原始等级”。
- **现状**：`types.ts` 的 `talents` 只有 `normal/skill/burst`；`validateCharacterBuild` 校验三级在 1..10。
- **风险**：命座/武器加天赋等级时，加成后的等级无法表达；调用方若直接传加成后等级，1..10 的校验会放过“实际 7 级+3 级”，且审计表里没有对应来源。
- **建议判定：采纳**。改动面小：`types.ts` 加字段、`build.ts` 校验 `modifiers[].levels` 为整数且来源 id 与 `requiredEffects` 一致、新增两条负例。不改公式与永久面板。
- **已落地**：`talents.modifiers` 为可选字段（省略 = 未建模，避免把 `level - original` 猜成来源）；校验 `source` 非空且已登记、`talent ∈ normal/skill/burst`、`levels` 为正整数；测试覆盖登记/未登记、非法天赋、0 级、非数组五种。

### D3 最终面板输入资格（`panelCheck.includedEffects`）

- **方案 §4.1**：第二种输入资格是“只有合成后的最终面板”，必须记录 `includedEffects` 的已知/未知状态；无法拆分条件、套装或共鸣时停在 legacy；**不能先假定全部未含再把效果加一遍**。
- **现状**：只有“原始配装可重建”一条路径。适配器读不到原始字段就报 `incomplete`，不会走面板路径——但也没有一句显式拒绝，无法证明“不存在第二条静默路径”。
- **建议判定：采纳（拒绝即可，不实现该路径）**。在 `types.ts` 或适配器出口增加明确的 `unsupported` 诊断（如“只有最终面板，不能证明已含效果边界”），并在 P0 文档写明 P0 不支持该输入资格。这样方案的第二资格在 P0 是“明确拒绝”而不是“未提及”。
- **已落地**：`CharacterBuild.panelCheck` 为可选字段，`validateCharacterBuild` 见到即报 `unsupported`（路径 `panelCheck`），不进入后续字段校验；P0 文档同步写明拒绝理由。

### D4 机制覆盖与误差界（`Coverage` / `errorBound`）

- **方案 §5、§9**：每个机制能力带 `state: verified | approximate | unsupported`、`source: SourceRef[]`、`limitations[]`、`errorBound: measured | unknown`；未知误差写 `unknown`，不填 0。
- **现状**：`PermanentData.effects[id]` 为 `verified-static | known-no-static | unsupported` + `modifiers` + `runtimeRequired`；版本用 `gameVersion/bundleId/source` 三元组核对。
- **差异**：现有审计是“每个效果 id 的状态”，方案是“每个能力 + 来源 + 误差界”。P0 没有误差样本，`errorBound` 必然全为 `unknown`。
- **建议判定：推迟到 P1**，P0 保持现有审计表。理由：P0 没有时间和逐 hit，误差界无从定义；现在引入只会造出一张全 `unknown` 的表。P0 文档补一句“机制覆盖与误差界在 P1 随动作/机制 fixture 引入”。

### D5 目标契约（`TargetConfig`）

- **方案 §5、§8.5**：目标预设 `dummy-lv100`（Lv100、标准防御、全抗 10%、无限血、静止、无敌盾/相位、无外部加成），并用 `placementScenarioId` 记录站位/领域覆盖假设。
- **现状**：`OrdinaryHit` 直接接收 `enemyLevel/resistance/defenseReduction/...` 数字；没有预设对象，也没有说明与 miao 默认 `enemyLv:103` 的区别。
- **风险**：调用方各自填数字，容易出现“以为在算 Lv100，实际传了 103”这类口径漂移；结果里也没有目标口径可回读。
- **建议判定：部分采纳**。P0 先加**只读的目标口径常量**（`dummy-lv100`：100 级、各抗 0.1、无限血、静止、无盾/相位）并在 `OrdinaryDamageResult` 回填 `target: { id, level, resistance }`；`placementScenarioId` 等到 P1 有动作时再引入。这样不改变公式，只固定默认口径。
- **已落地**：`formula.ts` 导出 `TARGET_PRESETS`（`dummy-lv100`），`OrdinaryHit.targetId` 可选；绑定后等级/抗性必须与预设一致，否则 `invalid`，未知目标 `unsupported`，结果回填 `target`（未绑定时 `id: 'custom'`）。公式与 factors 未改动。

### D6 数据包身份（`bundleHash`）

- **方案 §5**：`SimulationInput` 含 `bundleId` + `bundleHash`。
- **现状**：`expected { gameVersion, bundleId, source }` 三项字符串核对，无内容 hash。
- **风险**：同一 `bundleId` 被改动内容后仍能通过核对；审计表“干净”不能证明底数没变。
- **建议判定：推迟，但需在 P0 文档写明限制**。当前没有正式数据包文件（基础数据由调用方传对象），hash 无处可算；等 `data/team-sim/<gameVersion>/` 落地（方案 §4）再加。现在要在 P0 文档写“三元组只证明标识一致，不证明数据未被替换”。
- **已落地（仅文档）**：P0 文档「永久面板」末尾写明 `bundleId` 不防篡改、哈希/签名等数据包落地再补。

### D7 legacy 结果类型

- **方案 §5、§7.3**：`LegacyResult { status: 'legacy-estimate', ... }`，与 `SimulationResult` 分别命名；旧关键词轴保留独立 legacy 模式，页面标注“兼容估算”。
- **现状**：P0 没有 legacy 类型，也没有模式开关。`#队伍伤害` 仍走原聚合行，等于“没接线”，而不是“有类型、有模式、有标注”。
- **建议判定：采纳（仅类型占位）**。在 `types.ts` 加 `LegacyResult` 与 `TeamDamageMode = 'legacy' | 'strict'` 的判别，P0 只用于输出标注，不改 `apps/teamDamage.ts` 行为。这样 P1 接线时不需要再改契约，也避免以后把 legacy 值当新引擎真值。
- **已落地（比原建议更窄）**：只加 `LegacyResult`（`status:'legacy-estimate'`、`mode:'legacy'`、`simulationReady:false`）与构造器 `legacyEstimate()`；未加 `TeamDamageMode` 判别，因为 P0 没有模式开关，空枚举只会多一层没接线的分支。新增 `test/team-sim-legacy.test.mjs` 断言口径标记与入参隔离。

## 三、P0 退出条件对照（方案 §12）

| 方案要求 | 现状 | 结论 |
|---|---|---|
| 四个独立单角色的永久面板/静态公式 fixture 通过 | 适配层 4 个角色；`test/team-sim-build.test.mjs` 已扩到 **4 个独立角色**（各自 `characterId/weapon.id/element/白值`，断言 4 个 id 互不相同、面板按各自白值计算） | 满足（仍为合成数据） |
| 明确不支持列表 | [docs/队伍模拟-P0底座.md](./队伍模拟-P0底座.md) 第 16 行有清单（含误差界推迟说明） | 满足 |
| 没有完整配装不进入正式模拟 | `incomplete` 分支，不产出面板 | 满足 |

补充事实：全部夹具是**合成数据**（`test/fixtures/team-sim/miao-builds.mjs` 的 id 为 `10000000 + index`、名字“合成角色N”、武器 `100 + index`），不是真实 miao 数据形态。“四个独立单角色”在结构上已满足，但角色身份与白值仍是维护者自造的，不能替代真实账号数据。

## 四、建议实施顺序

## 五、仍未决、需作者定

- 真实角色 fixture 的来源：用维护者提供的 miao 原始数据，还是先从公开面板构造？方案 §10.2 要求 `input.json` 与视频证据，P0 阶段可先只做“面板 fixture”。当前 P0 退出条件按结构满足，但数据仍为合成，不能声称已通过真实角色验收。
- **精炼/突破身份**：原状是 `weapon:<id>`、`character:<id>` 不带档位，R1 与 R5、突破 5 与 6 的 `verified-static` 会互相套用。**已按作者选定的方向改掉**：来源 id 内置真实档位——`character:<id>:a<突破>`、`weapon:<id>:r<精炼>`，审计表按档位逐条登记，只登记另一档位时报缺来源；`PermanentData.weapon` 仍不带 `refinement` 字段，精炼只体现在来源 id 上（改 `weapon:<id>` 的旧数据需要同步改审计表键名）。未采纳“在 `PermanentData` 补 refinement 并做字段核对”的替代方案。
- 方案的效力：本文只把它当参考设计，不作为验收依据；若作者希望某些条目（如 D3 的拒绝路径、D7 的类型）成为硬约束，需要写进 [docs/队伍模拟-P0底座.md](./队伍模拟-P0底座.md)。
